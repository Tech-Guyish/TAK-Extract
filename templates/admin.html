TAK Server connection

The TAK Server database this tool reads from; a saved change takes effect on the next request.

Host depends on how this app is running, not just where Postgres is. Bare metal, same machine as TAK Server: 127.0.0.1 (or localhost). Docker, same machine as TAK Server: 127.0.0.1 is not correct — that's the container's own loopback. Run ./connect-database.sh from the repo instead; it finds the real address and configures what's needed to reach it (firewall, Postgres's listen_addresses / pg_hba.conf), asking before anything disruptive. Separate server (a split/HA install): enter that server's address, and make sure its Postgres accepts connections from this machine and no firewall blocks the port.

Port and Database default to TAK Server's own values (5432, cot) if left blank. User: a dedicated, least-privilege read-only account for this tool, not TAK Server's own database user — there is no default on purpose.

Backup & restore

One file: the audit log, every user account, and the connection settings (not the password).

Everything needed to move this installation to another machine. The TAK Server password is deliberately left out — live credential material does not belong in a downloaded file. The new machine supplies its own, the same way this one did (its .env, or entered once above).

Restore replaces everything on this machine — every user, every audit log entry, every connection setting — with the uploaded file's contents. A safety copy of what is here now is kept only until the restore succeeds, in case the upload is bad.

Which database exports come from

Every export records which database it read, so a package can be told apart from one produced against a different server. Where the read-only account has been granted EXECUTE on pg_control_system() (offered by connect-database.sh) that is the cluster's own identifier, fixed when the cluster was created and unchanged by restarts, address changes or TAK Server upgrades. Without that grant it falls back to catalog identifiers - the database name and a pair of OIDs - which any account can read but which are small numbers two unrelated servers could match by chance. The package says which of the two it got.

A difference between what this connection reports now and what recent exports recorded is worth knowing about, but it is not in itself a sign that anything is wrong: a rebuilt, upgraded or restored cluster reports a new identifier while holding the same data.

Database structure

A TAK Server or PostgreSQL upgrade can change the database underneath this tool. Most of what that breaks is loud - a query against a table that no longer exists fails, and the package README says which file failed and why. What is quiet is structure that changed and still works: a column added to cot_router changes what cot_router-raw.csv contains, and a geometry column in a different SRID makes the map-area filter return nothing rather than raise an error.

This compares the tables, their columns and types, and the PostGIS geometry columns against the record made when connect-database.sh connected this tool to the server. The same comparison runs inside every export, and its result is written into that package's README and its audit entry - so what the structure was when a package was built is recorded with the package, not only here.

A difference is not in itself a sign that anything is wrong: an upgrade changes structure legitimately. It is recorded so that it is known rather than assumed. Approve accepts what is there now as the new baseline; the log records who approved it.

The fuller check - which runs every statement an export sends - is ./check-database.sh on the server. Run it after an upgrade.

Re-check folder on the TAK Server

One-time setup on the TAK Server host, so the Export page's re-check line has somewhere to keep its files. If connect-database.sh ran on this host, it is already done - the line below is for a server that never ran it, or to add another administrator to the group later.

Checking…

After an export, the Export page shows the administrator one line to paste on the TAK Server. It re-runs the package's statements with psql and keeps the results, per case, under /var/lib/takextract/recheck/<case>/<date-time>/, with a RECHECK-INFO.txt beside them. That folder is the evidence copy of the server's own answer, and it outlives the server's retention purge.

psql runs as the postgres account and must be able to write there; the administrator must be able to read, move, archive and delete the files without sudo. So the folder is owned by postgres, in an operating-system group takextract that holds postgres and the administrator accounts, with mode 2770 (the group inherits down; nobody else can see it). A group, not a login: nothing new can sign in anywhere. It is file-system permission only and has nothing to do with the database role above or its privileges - the package README's "write privilege on cot_router: none" is unchanged.

Run the line once per server, logged in as the administrator who will do re-checks; then log out and back in so the group applies. To let another administrator manage the files later: sudo usermod -aG takextract <account>.

sudo groupadd -f takextract && sudo usermod -aG takextract postgres && sudo usermod -aG takextract $USER && sudo mkdir -p /var/lib/takextract/recheck && sudo chown postgres:takextract /var/lib/takextract/recheck && sudo chmod 2770 /var/lib/takextract/recheck

Map and privacy

What the maps on the Export and Verify pages may contact. Site-wide.

Both are on by default, which is how every install has worked so far.

Address search sends whatever is typed into the box in the map's corner to OpenStreetMap's public Nominatim service. A street name is a lookup; a case address typed into it is a disclosure to a third party, and the operator cannot take it back. Off removes the box entirely.

Map tiles are fetched from OpenStreetMap as you pan and zoom. No case data is sent, but the pattern of requests describes which area is being looked at. Off leaves the map blank - you can still draw an area and the Selected area panel still reports its coordinates, but there is no geography under it, so only turn this off if that trade is worth it.

Changing either is recorded in the audit log: it changes what this install discloses, so who changed it belongs on the record.

Audit log integrity

Every entry is chained to the one before it by a SHA-256; this recomputes the whole chain. Read-only.

Each audit entry stores a hash of its own content together with the previous entry's hash. Editing, deleting or inserting an entry after the fact changes what the chain would compute from that point on, so a walk from the first chained entry to the last either reproduces every stored hash or names the first entry that does not. Entries written before chaining was added carry no hash and are reported as predating it, not as broken. The delivery note an export entry gains when its download completes is the one change excluded from the hash.

The downloaded audit log carries the same two hash columns, so the chain can be checked outside this tool as well.
