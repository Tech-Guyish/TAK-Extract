What each file contains↑ top

TAK Server can export its own KMZ; this tool produces a locations KMZ (the Locations Package Only preset) and a full evidence package (the Full Evidence Package preset, which bundles the KMZ inside it). They are not equivalent. The grid shows what each one actually carries, so it is clear which to use when the question is not just "where were they?" but "what else was going on, who produced this, and can it be checked later?"

Export↑ top

The Export page retrieves location records from the TAK Server and packages them into a file. You set the area and time window, review how many records match, choose which files to include, and generate the export. No file is produced until you select Generate Export.

1. Draw the area

Draw a rectangle on the map to set the geographic area. Drawing a new rectangle replaces the old one; the trash control clears it. The Selected area panel underneath shows the exact coordinates you've chosen.

Movement trails and shape outlines. Faint gray dashed lines on the map show where devices moved during the selected time window, and darker dashed outlines show drawn shapes — fire lines, perimeters, circles — as they last stood in that window. Both cover the whole visible map rather than only the rectangle you have drawn, so a device traveling just outside the selection, or a shape whose anchor point falls outside it, is still visible and the rectangle can be adjusted before you export.

Shapes from automated feeds. Some shapes on a server were not drawn by anyone: software pushed them — an imported map layer of boundaries, for example — and the record says so, because the pushing software writes an element into it (__nodered, from Node-RED's TAK node) that a shape drawn at a map does not carry. Those shapes are left out of the map's outlines, shapes.csv and the KMZ unless you tick Include shapes from automated feeds in the Drawn shapes panel beside the selected area. Either way the package README states what was found and what was done with it, and manifest.csv names each such shape with that reason; cot.csv and the raw file keep their rows.

Trails and outlines appear once the map is zoomed in far enough; at wider views they are not drawn. They redraw as you pan, zoom, or change the time window. Only devices that moved are shown, and a trail breaks where that device stopped reporting. Neither carries identity — nothing is labelled, filled with its original colour, or clickable — and displaying them is not recorded in the audit log.

⚠ The search box in the map's corner sends whatever you type to OpenStreetMap's public Nominatim service. It is the only control on this page that contacts an outside service, so treat anything entered there as leaving your network. Drawing on the map sends nothing.

2. Set the time window

Set a Start and End date and time. The note beside the panel states which timezone the times are interpreted in. The window recorded here is what the Verify & Replay page later checks a file's actual data against.

3. Check the counts before exporting

Once you have an area and a time window, the counts box fills in: total position records, how many distinct IDs they came from, and a breakdown by kind — Personnel, Vehicles/equip, Infrastructure, and Map objects.

These are counts only; no names or positions are retrieved. Use them to adjust the area or time window before generating an export that turns out larger or smaller than intended.

4. Channels (optional)

TAK separates traffic into channels so one group only sees what's meant for them. This panel lists the channels actually seen in your chosen area and window, and lets you narrow the export to specific ones. Select all / none toggles them together.

Not every file can be channel-filtered — each file's own ⓘ About says whether it can. Anything excluded by a channel filter is recorded in the export's manifest, so a filtered export still accounts for what it left out.

5. Choose the files

Start with a preset — Locations Package Only for just the map/location data, or Full Evidence Package for the complete set — then adjust individually. Select none clears everything.

  • ⓘ About on each file says what it contains, what narrows it (time, area, channel — they differ per file), and flags anything especially sensitive.
  • Preview shows the column headers and first five rows that file would contain, using the same query the export itself runs. Because a preview displays real record content, it is recorded in the audit log. A file that is built from parsed geometry rather than a direct query (drawn shapes) has no row preview; its About note describes it instead.

6. Generate

Fill in Case / Incident and Exported For, then select Generate Export. Both fields are required; the button tells you which one is missing. The file builds and downloads, and the account running the export and both of those values go into the audit log alongside what you requested. The two values stay in place afterwards, so a series of exports for the same case does not mean retyping them.

You are not asked for your own name. The account you signed in with is recorded automatically and cannot be overwritten by anything entered on the page. The Exported For field identifies the person the export is being run on behalf of, which is the usual case when an administrator retrieves records for someone else. It appears in the Audit Log's For column and inside the package.

The result box shows the file's SHA-256 hash with a copy button. It was calculated when the file was built and written to the audit log before the download began; the Verify & Replay page looks a file up by it. Note it with the case, and keep the downloaded file as received — work on copies, since re-saving a CSV in a spreadsheet changes it. A re-run is a new file with its own hash.

Every export is recorded in the audit log whether it succeeds or fails. The entry covers the request itself — account, time, window and area — and contains no location data.

Optional: the re-check on the TAK Server

This one is not a step in exporting. A package and its entry in the audit log stand on their own; a package without a re-check is not deficient. The re-check is corroboration over and above what is required, and it is worth having when it is easy to get — which is now, while the server still holds the rows.

Everything in the package was read from the TAK Server database by this tool. The re-check is the same statements run again on the server by the administrator with psql — files this tool never touched. Once a package has downloaded, the page shows one line to paste on the server, with the case name and this page's address already in it.

  1. SSH to the TAK Server, paste the line, press Enter, enter your sudo password. The line fetches the package's queries.sql from TAK-Extract (the same bytes as in the zip — its hash is in SHA256SUMS.txt), runs it with psql in one read-only snapshot, hashes every result, tars the folder, and posts only the list of hashes back to TAK-Extract, which records it in the audit log and answers with a RECHECK-INFO.txt saved beside the files. No location data travels either way. Every statement is a SELECT.
  2. The last line printed is the verdict: recorded: … cot_router-raw.csv matches the package: yes. That is the hand check done for you — the <case>-recheck-cot_router-raw.csv line in the server's hash file against the <case>-cot_router-raw.csv line in the package's SHA256SUMS.txt. The tool writes that file the way psql writes CSV, with every value in the server's own text form, so the same rows give the same bytes; a match means the file the server wrote and the one in the package have the same hash. The other re-check files are recorded, not compared by hash — they can be compared by content, and the package README says under WHAT THE RE-CHECK COMPARES why hashing them would report differences that are not errors. Both hash files are in the case folder for anyone to compare by eye.
  3. If the moment passes. The line above is shown once, on this page, and the token in it lasts 48 hours. It is no longer the only way in: open the export's entry in the Audit Log and use Re-check this extraction, and a fresh line is issued for that package whenever you need it. The script is the one the package was built with, kept here since the export and checked against the hash the log recorded for it before anything is offered.
  4. The files stay on the server, in /var/lib/takextract/recheck/<case>/<date-time>-<package>/: the script that ran, every result, the snapshot file, the hash file, a .tgz of all of them, and RECHECK-INFO.txt. A second run goes in its own folder, and so does the re-check of a second export under the same case — the folder carries the time to the second and the first eight characters of that package's SHA-256, so several exports for one case (different areas, different channels) never write over each other and it is plain which export each folder re-checks. Nothing needs bringing back; WinSCP can copy the folder off for a production, or the raw file for a row-by-row diagnosis if the verdict was NO.

First time on a server: the folder and its permissions are created once, by connect-database.sh or by the one-time line on the System page (Re-check folder). Self-signed certificate: if this page's address shows a certificate warning, tick the box so the server's curl accepts it too. Other ways to run it: the button under the command opens a plain psql form for any machine that can reach the database — a server that cannot reach TAK-Extract, or psql on your own PC. Nothing is posted back that way, so the verdict is yours to check by hand; the README in the package gives those steps too.

You do not have to decide which method to use. Paste the line and watch: whether the TAK Server can reach this page is not something the page can test — that connection runs the other way — but it sees the server fetch the script, and it sees the hashes arrive. The line under the command follows along: waiting for the server to fetch the script, then the server fetched the script — psql is running, then the verdict in green or red. If nothing reaches it, it says so after a minute or two and points at the other methods, rather than leaving you to guess.

Do this at export time. The server deletes records after its retention period; after that no re-run is possible by anyone, and the package is the only copy.

Verify & Replay↑ top

This page has two functions, both performed on a file exported from TAK-Extract. It verifies the file by checking its hash against the audit log's record of exports, and it replays the movement it contains on a map. Both run entirely in your own browser; the file is never uploaded, and only a short fingerprint of it is checked against the server.

1. Load a file

Drag a full evidence package (.zip) or a locations map (.kmz) onto the drop box, or click the box to select one. Files this tool produced — from the Export page's evidence package or locations download — are both verified and replayed. A KMZ exported by TAK Server itself, or by another tool, replays too if it carries timestamped positions or tracks, but cannot be verified (see below).

The file is read entirely in your browser. Only its SHA-256 hash is sent to the server, to look up in the export audit log. No file contents and no location data leave your machine. To load a different file, refresh the page.

2. The verdict

Above the tabs, in one block: what this package is. Each line is a separate question, answered or honestly left unanswered, so the tabs below do not have to be read and interpreted to work out where things stand.

  • Whether the package is in this tool’s audit log — and if it is, when it was exported, by which account and for whom. If it is not, that is said plainly: it can mean the package came from a different install, or was altered after it was built, and on its own it is not proof of tampering.
  • Whether every file inside matches the list built with the package — each one hashed in your browser and compared with the package’s own SHA256SUMS.txt. Any that differ are named. Nothing is sent to do this and nothing is recorded.
  • Whether the records fall inside the window that was asked for, where the log holds enough to tell.
  • Whether an administrator’s re-check was recorded. If none was, that is stated as a fact rather than marked as a failure — a re-check is corroboration over and above what is required, and a package without one is not deficient.

The second line and the first say different things, and the page keeps them apart. SHA256SUMS.txt lives inside the zip, so on its own it shows the files agree with the list that arrived beside them. It is the first line — the whole package’s hash matching the log — that ties that list to the tool that built it. When the first line does not match, the second says so instead of implying the stronger result.

Produce the certification… appears here when the package is in the log. It returns a certification for a records custodian with the facts already filled in from the log — the package’s hash, every file’s hash, and the re-check’s results where there was one — leaving only the declaration and the signature for a person to complete, with counsel.

The result tabs

Under the verdict, three tabs sit in a row above the map: Hash check, File contents and Compare. They are the detail behind the verdict — there is no need to open any of them to know where a package stands. Each tab shows its one-line result and takes its state colour — green for a match, red for no match or a disagreement, neutral otherwise — so the state of a file can be read at a glance without opening anything. Select a tab to open its detail beneath the row; selecting another swaps to it, selecting the open one closes it. Only one is open at a time, so the map stays close to the top of the page.

3. Hash check

Calculates the file's hash and looks it up in the audit log. A match shows the entry recorded at export time: the account that ran the export, who it was run for, when, and the time window, area and any channel filter requested. No match means no export recorded here has this hash.

The Audit match line reports a second, separate check: whether the file's actual data — its earliest and latest report times — falls inside the window that was requested. A requested window is often wider than the data returned within it, so the two are reported separately rather than treated as the same fact.

4. File contents

A summary taken from the file itself: how many people and other entities it covers, how many position records it holds, and the time range those records span. These figures are calculated from the file's own contents rather than looked up, so they describe the file in front of you.

5. The map and playback

Once a valid file loads, the map appears with everything in it, and the playback controls below drive time.

  • Time readout & scrubber: the readout shows the moment currently being displayed; drag the scrubber to jump to any point in the file's time range.
  • Play / Reset to start: Play animates forward through time; Reset returns to the beginning of the window.
  • Speed: how fast playback runs relative to real time — from 1× (real time) up to 14400× (four hours of activity per second) — for skimming a long file or watching a short window closely.
  • Click a point on the map for that report's full detail. (Full detail is available when the loaded file is a .kmz or a .zip containing a .kmz; a package's cot.csv has no pre-built detail block, so it shows a name and time instead.)

6. Device activity timeline (the ribbon)

A timeline showing when each device was reporting across the period the file covers, including any gaps where a device stopped reporting. The Ribbon bars control shows or hides the per-device bars, which are hidden by default.

7. Display style

How each device is drawn as playback runs:

  • Current Position — a single dot showing where the device is at the moment being displayed.
  • Current Position & Trail — the dot plus a line tracing where it has been.
  • Current Position + Breadcrumbs — every individual GPS report as its own dot, plus a larger dot for the current position.
  • Breadcrumbs — every individual report as its own dot, with no connecting line, so reporting frequency and gaps are visible rather than smoothed over.
  • Trail/breadcrumb length — how far back the trail or breadcrumbs extend behind the current position, from 5 minutes up to All. This is a separate control from the scrubber: the scrubber sets the moment being displayed, and this sets how much history is drawn behind it.

8. Who and what is shown

  • People & other tracked entities — one colored entry per device. Click an entry to hide or show that device on the map. Show names on map labels each device with its callsign.
  • Channels (shown when the file carries them) — click a channel to hide or show everyone on it at once; Select none / all toggles them together. A device can belong to several channels.
  • Other markers — dropped points, drawn map objects and other markers that cannot represent a tracked person. These are hidden by default to keep the map focused on people, and the section can be opened to show any of them. Note that a drawn shape's anchor point also appears here as a single position record; the shape itself is drawn on the map (see Drawn shapes, next). Two further groups may appear here: Not GPS-tracked (placed by hand), covering items whose positions were placed by a person rather than measured by a device, and Moved here manually, covering entities you have moved yourself using the control below.
  • Drag to re-file — a device can be dragged between the "People & other tracked entities" list and "Other markers" when the automatic sorting has placed it in the wrong one. This changes only how the device is grouped in your current view; the file and its data are unchanged.

9. Drawn shapes

Fire lines, perimeters, circles and other drawn map objects from a full package are drawn as they stood at the current playback time. A shape that was redrawn changes as playback moves, and one the server recorded as deleted disappears at that moment. Shapes are always drawn beneath people, so a filled area never hides anyone, and a shape drawn inside another stays on top of it.

Click a shape on the map for its details: which version is shown and how many there are, when that version began, who drew or edited it, its size, and whether it was later replaced or deleted. The Drawn shapes list works like the people list — click an entry to hide or show that shape, or use Select none / all.

10. Compare: the re-check

The third tab shows the administrator's re-check (Export, the optional re-check) as soon as the package loads: green if the server's cot_router-raw.csv hash matched the package's, red if not, with when it was recorded, under which account, where the files are on the server, and the hash of the .tgz. Nothing to choose — the record was written when the server posted its hashes.

For a mismatch, fetch <case>-recheck-cot_router-raw.csv from the server folder and select Choose a re-check file: it is compared with the package's own cot_router-raw.csv exactly by row id — every id present on both sides with identical values — and any difference is listed by id and field. The file's SHA-256 is shown and looked up; signed in as an administrator, Record this file writes it to the audit log too.

A KML/KMZ has no row ids, so a KML/KMZ compared here is matched by callsign, time and position (within 1 second and 1 metre) with a per-device table and, for any unmatched positions, the likely reasons. Files are read in your browser; only a SHA-256 hash leaves it, and only when an administrator records one.

Sharing an export & using other viewers

The locations file (.kmz) this tool produces is a standard KMZ, not a proprietary format. It opens in Google Earth or any other KML viewer, showing the points, track lines and per-point details, and replaying the same movement through that viewer's own time slider. Drawn shapes from a full package — fire lines, perimeters, circles — are included as real geometry, one entry per version, each shown on the time slider only while it was current, so a line that was redrawn changes as the slider moves and a deleted shape disappears at the moment the server recorded its removal. This makes an export straightforward to hand to someone who does not have access to this tool.

What those other viewers can't do is check it against the audit log. That check — looking the file's hash up in this installation's record of exports — is unique to this page. Use Google Earth or a similar viewer to view or share an export, and use this page whenever the question is whether a file is one this tool recorded.

Files from TAK Server or other tools. A KMZ exported by TAK Server itself — or by ATAK, Google Earth, or another tool — replays here if it carries timestamped positions or tracks: the page reads each device's track and any timed point and shows them as the file states them. Anything without a timestamp (drawn shapes, untimed points, lines) cannot be placed on a timeline; the summary counts how many were left out rather than dropping them silently.

What such a file cannot get is verification. It did not come from this installation, so there is no audit-log entry to check it against; the hash check shows no match and the file summary says NOT PRODUCED BY THIS TOOL. Positions are replayed exactly as the file states them — nothing here confirms they are genuine or complete.

Using an export as evidence↑ top

Two questions follow an export into a report or a courtroom: is this the file that was produced? and is what it holds what the server held? This section lists what the tool records for each, and what none of it can say. It is not legal advice; what a court requires is a question for counsel.

What the package and the log record

  • The file. Its SHA-256, calculated when it was built and written to the audit log before download; a hash for every file inside it (SHA256SUMS.txt). Recompute with any standard utility — Get-FileHash, certutil -hashfile, sha256sum — and compare with the audit log; no tool needed.
  • The read. The README states, as the database answered: every statement ran in one repeatable-read, read-only transaction (the snapshot id is printed; the server refuses a write inside it); the account used and the write privileges the database says it holds; the database clock beside the tool's; the version and git commit of the code that ran.
  • The statements. queries.sql: each one exactly as sent, with its values. Readable, and re-runnable (Export, the optional re-check).
  • The server's own rows. cot_router-raw.csv: every column of every position row as stored, unmodified, in the server's text form — the closest thing to the server's record a file can be, and the copy that outlives the server's retention period.
  • The re-check. The administrator's own re-run on the server: the results kept per case under /var/lib/takextract/recheck/ with a RECHECK-INFO.txt (the copy that outlives the server's retention purge), and its hashes recorded in the audit log the moment they were posted (Export, the optional re-check; Verify step 10). Corroboration over and above what is required — a package without one is not deficient.
  • The log itself. Every entry is chained to the one before it by hash; an edit, deletion or insertion after the fact is detectable (System → Audit log integrity, or from the downloaded log).
  • How to check it. VERIFY.txt in the package: the one command that checks every file at once, what a failed line means, and what the check does and does not show — for whoever receives the package and has no access to this tool.
  • Which database it came from. Recorded in the package README and in the audit entry, so a package can be told apart from one produced against a different server (System → Which database exports come from).
  • A certification. Produced from Verify & Replay with the facts above, every file's hash and the re-check's results already entered, leaving the declaration and signature for a records custodian to complete with counsel. It is generated on demand rather than shipped blank in the package, because by the time anyone fills it in the log already holds every value it used to leave as a blank.

Which artifact answers which question

  • "The file changed." — the package hash against the audit log; the per-file hashes.
  • "The tool copied wrongly." — the raw rows (nothing parsed); the administrator's re-check (a second person, a second program); the public source.
  • "The query was wrong." — queries.sql is readable.
  • "The files were read at different moments." — the snapshot: one transaction, one instant.
  • "The tool could have altered the server." — the account's privileges as the database reported them; a read-only transaction the server enforces.
  • "Which code ran." — version and commit, in the README and the log.
  • "Who did what, when." — the audit log: export, download, re-check record; chained.
  • "The positions are accurate." — nothing here can say. The data carries what a witness needs: servertime (the server's clock, the one an agency controls) beside event_time (the device's); the fix source (GPS, accuracy unknown, placed by hand); the accuracy figure the device reported; device model and software. A callsign is the name a device used, not who carried it; where the server recorded nothing, the file says so.

The audit log lives in this tool's own data, not in TAK Server. Back it up (System → Backup) and treat it as part of the evidence trail.

Audit Log↑ top

A record of every export request the tool has handled: who ran it, what was requested, when, and the outcome. It is the provenance record for any file this tool has produced.

What the log records

The log records the shape of each request — no location data. You can see that someone exported a given area and window, but not where anybody was.

Every entry carries the version and commit of the code that wrote it, and two hash columns: a SHA-256 of the entry's own content and the previous entry's hash, so the log is a chain. The System page verifies it; the downloaded log carries the same columns, so anyone can. Entries from before chaining was added have no hash and are reported as predating it, never as broken.

Besides exports and log downloads, the log holds companion entries: an administrator recording the hash of a re-check file beside the package it was made for (Export, the optional re-check; Verify step 10). The entry names the file, the package's hash and how many rows matched.

Two identity fields are recorded in separate columns. Who ran it is the account that was signed in; it cannot be entered by hand or altered by the person requesting the export. For is entered by the operator at export time to record who requested it, and is not verified identity. They are stored separately so that an entered note is not read as a verified one.

Reading the log

The log opens as one line per case, most recently active first. Each line gives the case reference, how many extractions it holds and how many events in all, when the last one was, and the case's verdict — the result of its re-checks, coloured, so a case that did not hold up stands out without opening anything.

Click the case and it opens into its extractions, oldest first and numbered: Extraction 1, Extraction 2. Under each one sit the events that belong to that extraction — the TAK Server fetching its script, the re-check that followed — so with several extractions for one case it is plain which re-check checked which export. Anything belonging to the case but not to a particular extraction (a file preview, a log download, a case correction) is grouped at the end under Other activity for this case.

Entries that belong to no case at all — a user added, the connection settings changed, a backup restored — are not cases and are not listed among them. They have their own Application-wide activity section under the case list, on every page.

Each line says in words what it was — Evidence package exported, TAK Server fetched the script, Re-check on the TAK Server, Case reference corrected. The recorded value behind that wording (package, recheck, and so on) is shown inside the opened entry as recorded as: it is what the row actually holds, what the downloaded CSV carries, and what the hash chain covers.

Click an entry and it opens in turn, listing everything that entry recorded:

  • What happened — the same plain wording, a sentence saying what that kind of entry is, and the recorded value behind it.
  • Recorded / Who ran it / For — the time in the server's own timezone, the account that was signed in, and who the operator said it was for.
  • Window / Area — the time range and geographic box requested, on the entries that have one.
  • Records, or Files hashed on the server on a re-check — the label says which, so a count is never read as the other thing.
  • SHA-256 of — the hash, with the file it is the hash of above it and a line saying its role. On an export that is the file you were handed; on a re-check or a recorded companion file it is the export the entry refers to, which is the value most easily misread as something the entry itself produced.
  • Files in the package, on an export — every file the package held and the hash it had when the package was built, folded away until asked for. That is what lets a single CSV handed over later be checked against the log without the package, and it is where the SQL query script's own hash is.
  • What was compared, on a re-check — the two files that were compared by hash, each named, each with its own result; then the count of the files that were recorded, not compared, and a line saying why. The full list of what the server hashed opens underneath, hash by hash. Nothing is coloured as a pass except a comparison that was actually made.
  • Files excluded — anything left out of that export, so a partial export still accounts for what it didn't include.
  • Re-check, on an export — Re-check this extraction issues a fresh line to paste on the TAK Server for that package, months after the export if need be (Export, the optional re-check). Asking is itself an entry, Re-check offered again, and if the kept script does not have the hash the export recorded, nothing is issued and that disagreement is what gets written down.
  • Detail — the rest of what was recorded, a clause per line, each hash with the name of the file it belongs to. For a re-check this is where the server, the folder its files are in, and the two verdicts appear.

Flat list (beside the filter box) switches to one line per entry across every case, newest first — for "what happened today" rather than "what happened to this case". Its column labels sort the whole log, not just the page you are looking at. By case switches back.

Correcting a case reference

A case typed wrong at export time repeats on everything that follows it — the package, the fetch of its script, its re-check. An administrator can put it right: Correct case… on a case line renames every entry recorded under it, and Correct this entry's case… inside an opened entry moves just that one. Both ask for the correct reference and, if you want, a reason, which is recorded with it.

Nothing already in the log is altered. The case is one of the fields the hash chain covers, so rewriting it would break that entry's hash and every link after it — the log would report itself as tampered, and that alarm has to keep meaning something. A correction is therefore recorded as its own entry, of kind case-correction, naming what was corrected, from what to what, by whom and why.

What you see afterwards: the case is listed under the corrected name and carries its entries and the correction entry together, while each corrected entry still shows Case recorded as with the name it was filed under at the time. The filter finds the case under either name, because both are things that really happened. A reader sees the mistake and the correction, rather than a tidy log that quietly disagrees with the package someone is holding.

Finding and exporting entries

  • Filter — narrow the list by case ID or the name of whoever ran the export.
  • Prev / Next — page through the log.
  • Download selected — tick what you want and download only that. A tick takes everything under it: on a case, all of its entries; on an extraction, that export and the events that checked it. This is the usual method, as most requests concern a single case.
  • Download entire log — exports every entry.

Downloading the log is itself recorded. Case / Incident and Exported For beside the buttons are required, as on the Export page, and a new entry is written for the download.

System↑ top

Setup and administration: who can sign in, how the tool reaches the TAK Server, backups, and updates. Available to administrators only.

Users and roles

Only people listed here can use the tool. There are two roles:

  • admin — Export, Audit Log, and this System page.
  • viewer — only Verify & Replay. A viewer can check and replay a file they've been given, but cannot pull new data out of the TAK server at all.

Assign viewer to anyone whose role is to examine an export rather than produce one; it grants no access to TAK Server data. When adding a user, Generate creates a strong password, Copy places it on the clipboard, and Show displays it.

TAK Server connection

The database connection this tool reads from: host, port, database name, user, and password. A status badge beside the heading shows the state of the saved connection: Connected (green), Disconnected (red, with the reason shown on hover), or Not configured (amber) when no settings have been saved. Select the badge to check again.

Test connection and the badge report different things and may disagree. Test connection checks the values currently entered in the form, which is useful when trying a new host before saving it. The badge reports the saved settings, which are the ones the tool uses; it refreshes after a successful Save.

The correct Host depends on how this application is running, not only on where Postgres is installed:

  • Directly on the TAK Server machine (no Docker): 127.0.0.1 or localhost.
  • In Docker on the TAK Server machine: 127.0.0.1 is wrong — inside the container it means the container itself. Run ./connect-database.sh from the repository; it finds the right address and sets up what is needed to reach it (the firewall, Postgres's listen_addresses and pg_hba.conf), asking before any disruptive step.
  • A separate server (split or high-availability install): that server's address, with its Postgres configured to accept connections from this machine and no firewall blocking the port.

Port and Database default to TAK Server's own values (5432, cot) when left blank. The User should be a dedicated read-only account with least privilege, not TAK Server's own database user; the tool never writes to TAK Server, and there is deliberately no default.

Backup & restore

Download backup saves this tool's own data — user accounts, settings, and the audit log. It does not include the TAK Server password, which is deliberately left out so a backup file isn't a credential leak; you re-enter it after a restore.

Restore replaces everything — every user, every audit log entry and every connection setting is overwritten by the contents of the backup. Confirm the file is the one you intend before proceeding. A safety copy of the current data is kept only until the restore succeeds, in case the upload turns out to be bad.

Which database exports come from

Every export records the identity of the database it read, so a package can be told apart from one produced against a different server. This panel compares that with what the connection points at now, which is the thing worth catching: the TAK Server connection is editable from this page, so an install can be repointed between exports and nothing else would say so.

Where the read-only account has been granted EXECUTE on pg_control_system() — offered by connect-database.sh, read-only, no access to any data — the value is the database cluster's own identifier, fixed when the cluster was created and unchanged by restarts, address changes or TAK Server upgrades. Without that grant it falls back to catalog identifiers: the database name and two OIDs, which any account can read but which are small numbers two unrelated servers could match by chance. The package states which of the two it used, and the panel says when it is the weaker one.

A difference is not in itself a sign that anything is wrong. A rebuilt, upgraded or restored cluster reports a new identifier while holding the same data. Equally, a match does not prove which machine was read: a replica reports the same identifier as the cluster it copies. The panel flags; it does not conclude.

Database structure

A TAK Server or PostgreSQL upgrade can change the database underneath this tool. Most of what that breaks is loud: a query against a table that no longer exists fails, and the package README prints *** THIS FILE FAILED TO GENERATE *** beside the file, with the reason. That case looks after itself.

What this panel is for is the quiet case — structure that changed and still works:

  • A column added to cot_router changes what <case>-cot_router-raw.csv contains. Nothing errors; the file is simply a different shape from the one an earlier package holds.
  • A geometry column in a different SRID makes the map-area filter compare against an envelope built in another coordinate system. It does not raise — it returns nothing, so an export looks clean and is empty.
  • A retyped channel-mask column stops decoding, so channel filtering silently matches nothing.

The panel compares the tables, their columns and types, and the PostGIS geometry columns against the record made when connect-database.sh connected this tool to the server. The same comparison runs inside every export, and its result is written into that package's README and its audit entry — so what the structure was when a package was built is recorded with the package, not only whenever someone remembers to look here.

Approve accepts what is there now as the new baseline. Use it once you have looked at a difference and it is expected; the audit log records who approved it and what was accepted. If the structure changes between the page loading and you pressing it, the approval is refused rather than letting you accept something you did not see.

A difference is not in itself a sign that anything is wrong, and this panel never says that it is. An upgrade changes structure legitimately. It is recorded so that it is known rather than assumed.

The fuller database check, after an upgrade

On the server, in the install directory:

sudo ./check-database.sh

This runs every statement an export sends — from the same code that builds a package, so it cannot drift from it — and then the handful of checks above that need real values rather than types. It is read-only throughout: every statement is a SELECT, in a READ ONLY transaction, under an account with no write privileges. It writes its verdict to the audit log like any other action.

Exit codes, for anyone scripting it: 0 all well, 1 drift or warnings, 2 something is wrong, 3 could not connect at all. A connection failure names what it usually is — a pg_hba.conf line a major-version upgrade did not carry across, a role that did not survive, a cluster left on a different port, or listen_addresses back at localhost where a container on the Docker bridge cannot reach it.

Once a difference has been reviewed and is expected:

sudo ./check-database.sh --approve-baseline --approved-by "your name"

A baseline records the structure as it is at that moment. If this tool was connected after an upgrade had already happened, the baseline captures the upgraded state — nothing can reconstruct what was there before. The statement pass and the SRID and decode checks still say whether today's database is sound; the baseline is what protects the next upgrade.

Re-check folder on the TAK Server

One-time setup per TAK Server so the Export page's re-check line has somewhere to keep its files: /var/lib/takextract/recheck, owned by postgres (psql writes there), in an operating-system group takextract holding postgres and the administrator accounts (they read, move, archive and delete without sudo), mode 2770. A group, not a login — nothing new can sign in — and file-system permission only, unrelated to the database role or its privileges. connect-database.sh does this as one of its steps and leaves a note in .env; the panel then shows Set up … with when and on which host, and, once a re-check has been posted, the newest one recorded. Without either it shows the same line for a server that never ran the script. Log out and back in after the setup so the group applies.

Audit log integrity

Verify audit log chain recomputes every entry's hash from its stored content and checks each against the next: intact, or broken at a named entry with the reason (content edited; an entry removed, inserted or reordered). Read-only. The one change an entry may legitimately receive after it is written — the delivery note added when an export's download completes — is excluded from the hash.

Check for updates

Compares your installation against the latest published version. The check is read-only: it installs nothing, and reports what is available along with the commands to apply it.

Appearance

Light, dark, or follow your system preference. The setting applies to your account only and does not affect other users.
