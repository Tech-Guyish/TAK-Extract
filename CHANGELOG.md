### v1.21.3 (BETA) — 2026-10-06

- 🐛 `Bug Fix` - **The update command says where to run it.** On a Docker install the System page printed `git pull` and the rebuild line with no directory, because a container cannot discover where its clone sits on the host - inside one the app only ever sees `/app`. Run from anywhere else that fails with `fatal: not a git repository`, which is what happened on a real install. `setup.sh` now records `HOST_INSTALL_DIR` in `.env`, which `docker-compose.yml` already passes into the container whole, and the command block always leads with `cd <path>`: the recorded one where there is one, an obvious `/path/to/your/TAK-Extract/clone` placeholder where there is not, with a line saying to replace it. Never a plausible-looking guess at a path the app does not know. An install made before this keeps working and shows the placeholder until `setup.sh` is re-run or the line is added by hand.

### v1.21.2 (BETA) — 2026-10-06

- 🔒 `Security` - **The https redirect no longer echoes the Host header back.** With `SERVE_TLS=true` a plain-http request was answered with a redirect built from `request.url`, which embeds the Host header verbatim - so a request claiming `Host: evil.example` was answered with `https://evil.example/<same path>`. Following that is the caller's own problem; a cache sitting in front of the app is not, because it would key the redirect on the path and could then serve it to somebody else. `SERVE_TLS` is documented as the no-proxy case, which makes that unlikely - but nothing in the code enforced it. The target is now built from the hosts this install actually answers to: `TLS_CERT_HOST`, or the detected LAN address, the same derivation the certificate's own subject uses, plus loopback. An unrecognised Host is redirected to the expected one rather than refused, so a misconfigured-but-honest request still lands somewhere usable. The port is kept so the redirect stays reachable, but only when it really is a port - re-reading the first version of this fix showed it carrying whatever followed the colon straight through from the same untrusted header, which is reachable with a raw `Host:` even though the test client's own builder rejects it.
- 🔒 `Security` - **A 403 page no longer renders a username as HTML.** The "signed in but has no role granting access to this page" response interpolated the username and returned it as a bare `Response`, which Flask serves as `text/html`. Nothing validates what characters a username may hold - an admin creates them in local mode, and in authentik mode the reverse proxy asserts them - so it is served as `text/plain` now, where any markup in it is inert.
- 🔧 `Improvement` - **`tempfile.mktemp()` is gone from the test suites.** It returns a name without reserving it, so anything else on the machine can take that name between the call and the open. Eleven call sites now use a `mkdtemp()`-based helper: the directory is created atomically at `0700` and the file inside still does not exist yet, which is what every caller wanted.
- 🔒 `Hardening` - **Three workflows declare what they need instead of inheriting it.** `tests`, `pip-audit` and `dead-code` carried no `permissions:` block, so they ran with whatever the repository default grants. They are `contents: read` now; CodeQL keeps `security-events: write` and the release archive `contents: write`, which are the only two that write anything.
- 📝 `Docs` - All four of the above came from **CodeQL's first run against this code**, which could never execute while the repository was private: code scanning needs a public repository or Advanced Security, so the workflow had been failing at its upload step since the day it was added. The first real run reported 36 alerts. Four were worth fixing and are above. Twenty-one were `py/stack-trace-exposure` on routes that are all `@require_role("admin", api=True)` - returning the database's actual error to a signed-in administrator is what makes *Test connection* worth pressing, and the viewer-reachable instances of that were fixed in v0.5.0. One was an open-redirect report on the login `next` parameter, which `_safe_next_path()` has guarded since v0.4.1. Each of those is dismissed on the alert with its reason rather than left open.

### v1.21.0 (BETA) — 2026-10-04

- ✨ `New Feature` - **Each release carries the SHA-256 of a source archive built for it** (`.github/workflows/release-archive.yml`). The archive is built with `git archive` at the tag, attached to the release, and its hash recorded in the notes along with the tag's commit and tree. Deliberately NOT the hash of GitHub's own "Source code" links: those are generated on demand and their checksums are not guaranteed to stay the same - on 2023-01-30 a git upgrade changed the compression and every one of them got a new checksum overnight, identical contents and all. GitHub's own guidance is to upload an asset for anything that needs a stable checksum, so that is what this does. The notes say the hash is of the attached file and what to run to check it, and nothing more; the tree hash is published beside it for anyone who would rather reproduce the identity from a clone than download anything.
- ✨ `New Feature` - **A third standing check: dead code and complexity** (`.github/workflows/dead-code.yml`), beside pip-audit and CodeQL. Ruff's pyflakes rules - unused imports, unused variables, unreachable code - and `vulture` for functions and attributes nothing references are hard failures. Complexity is printed but never fails: the dozen functions it names are long because the job is long, and splitting them to satisfy a threshold would be churn dressed as cleanup; printing them means the list cannot grow unnoticed. `ERA` (commented-out code) is deliberately off - it read a sentence in a comment as code, which is how a check teaches people to ignore it. Vulture cannot see Flask's `@app.route`, so the registration decorators are named on the command line and three attributes the standard library reads back are listed in `.github/vulture-whitelist.py`, each with the library that reads it.
- 🔧 `Improvement` - **One copy of the escape that keeps a callsign from being read as HTML.** `esc()` was written out separately in index, verify, audit and admin. The copies had drifted apart once already - a comment left behind in two of them recorded that the weaker version had ended up in the page rendering the most hostile data - and they were still textually different, so nothing stopped it happening again. `esc()`, `csrfHeaders()` and `copyToClipboard()` now live in one `templates/_shared.js.html` that the four pages include. Not served from `/static`: Flask's static handler answers without a session, and every URL this app serves sits behind the same login gate. No behaviour changed - the browser suite drives all five real pages and passes unchanged.
- 🔧 `Improvement` - **The export now calls the function that was written for it.** `shapes.build_rows()` assembles the drawn-shape rows and their seven-key summary in one call; `exports.build_package()` was doing the same two steps and rebuilding the same summary inline, so the summary existed twice and `build_rows` was reached only by the tests - which meant the shape tests were exercising a shortcut the export never took. `build_rows` now also returns the collection (the KMZ's drawn-shapes folder is rendered from it), and `build_package` calls it. Ten duplicated lines gone, one definition of the summary, and the tests are on the real path. Five f-strings with nothing to interpolate were removed at the same time.
- 📝 `Docs` - **Repository history was rewritten, so every commit hash changed.** No file content moved - the rewritten tree hashes identically to its predecessor. An existing clone cannot `git pull` across that - run `git fetch && git reset --hard origin/master` once on each machine instead. One consequence worth stating plainly: each audit entry records the version and commit of the code that wrote it, so entries made before this will name commit hashes that no longer exist in the repository. The entries themselves are untouched and the hash chain over them still verifies - what breaks is only the lookup from a recorded hash back to the code.
- 🔧 `Improvement` - **The Verify page no longer opens on one particular region, and neither do the test fixtures.** September's pass removed a hardcoded county map default from the Export page and left a comment there saying why it must not be a specific place. Four spots were missed, and together they traced the same bounding box over one jurisdiction: the Verify & Replay map's opening view (`38.9, -77.4` at zoom 9, shown until a dropped package's own `fitBounds()` lands - the only one of the four a user ever saw), the schema check's probe box, `test_exports.py`'s window constants, and the coordinates throughout `test_browser.py`'s fixtures. Verify now opens on the same neutral continental view as the Export page, for the same stated reason. Every fixture was moved by a fixed offset onto the Smith County, Kansas area the Guide's screenshots already use - a pure translation, so each shape's relative geometry and each distinct value is preserved, which the suites confirm. Nothing about what the tool reads or produces changed.
- 📝 `Docs` - **A claim about Postgres that was wrong in three places.** The README, `exports.py`'s docstring and `connect-database.sh`'s comment all said that `pg_control_system()` - the function that gives each export its strong source-database identifier - is restricted to superusers until granted. It is not. On a stock cluster the function carries no privilege list of its own, so Postgres's default applies and any role can call it: `pg_proc.proacl` is NULL for it on PostgreSQL 18, checked on two clusters, and the documentation names a superuser restriction for the server-signalling and recovery-control functions while saying nothing of the kind for the control-data ones. The effect of the error was to make the installer's grant step look like a hurdle and the weaker catalog fingerprint look like the normal outcome, when the step usually finds the privilege already there and grants nothing. **No code changed** - the privilege can still be revoked, so it is still checked rather than assumed, and the fallback still exists.
- 📝 `Docs` - **It reads as a tool for any team that has to account for where its units were, because that is what it is.** It was built for a law-enforcement records-request workload and the README's first line said so, which made it look inapplicable to search and rescue, fire and emergency management - all of which run TAK Server, and all of which get asked the same question months later. The first line now names records requests and after-action review, with those kinds of team named under it. The security policy opened "TAK-Extract reads law-enforcement location data"; it now says it reads the recorded movements of real people, put in front of courts, review boards and records requesters. In the package README that travels with every export, "officers and vehicles carry devices" is now "people and vehicles", and a suggested cross-check against "an officer's own account" is now "the account of whoever carried it". Wording only - no file, column or count changed. The pages inside the tool needed nothing: Case / Incident, records and evidence package were already neutral.
- 🔧 `Improvement` - **The repository's own layout: the test suites and the written material each moved into a folder.** Thirty-six things in the root directory, most of them files nobody opens, made the GitHub page read as a pile rather than a map. The eight `test_*.py` suites are now in `tests/`; the security policy, the evidence-standards reference and the third-party notices are now in `docs/`, along with the User Guide's screenshots (`docs/guide-images/`, previously `guide_images/`). Twenty-five entries instead of thirty-six, and the README gained a **What's in this repository** table so the ones that remain say what they are. **Nothing an administrator types changed** - `./setup.sh`, `./connect-database.sh`, `./check-database.sh` and the update commands still run from the checkout root, and `Dockerfile`/`docker-compose.yml` stayed there with them so `docker compose` needs no `-f`. The suites are still run one file at a time, now as `python tests/test_exports.py`; CI runs them from the new path, and the Docker image excludes `tests/` as a folder rather than naming two of the files inside it.

### v1.20.3 (BETA) — 2026-10-04

- 🐛 `Bug Fix` - **The schema check crashed on any install that had recorded an export.** `./check-database.sh` died with `TypeError: unhashable type: 'dict'` before printing anything: the list of databases recent exports came from is a list of dicts, and the check treated them as strings. It only fires once the audit log holds an export that recorded a source database - a fresh install returns an empty list and takes another branch - so every test install missed it and the production one failed on its first run.
- 🐛 `Bug Fix` - **And the comparison it unmasked could never have matched.** An export records the source database with its kind - `cluster <n>` or `catalog <db>/<oid>/<oid>` - while the check compared the bare identifier with no prefix. That comparison had never actually executed (it raised on the dict shape first), so the mismatch shipped unnoticed. The effect would have been a permanent WARN on every run of a correctly configured install: two values printed that read the same, declared different, a non-OK verdict written into the hash-chained audit log each time, and a real repoint lost in the noise. Now compared through the same function the log is written from, with the kind deliberately kept in the comparison so a catalog fingerprint can never read as a cluster identifier of the same number.

### v1.20.2 (BETA) — 2026-10-04

- 🐛 `Bug Fix` - **A run that leaves `DB_PASSWORD` empty now says so.** An existing database role's password cannot be read back, so a run that finds the role already there has nothing to write into `.env`. If `.env` was recreated in the meantime - `setup.sh` builds a fresh one whenever there is none - the value was left empty while the summary still reported ".env: updated", which reads as success. The first symptom was an unrelated-looking `fe_sendauth: no password supplied` several steps later. **The warning deliberately does not claim the app cannot connect**: `.env` is not the live source, since the app reads the password saved on the System page first and falls back to the environment only when nothing is stored there. It sends you to the System page first, and if you do rotate the password, tells you to re-save it there as well - otherwise the previously saved value keeps winning and the new one is ignored.
- 🐛 `Bug Fix` - All five `.env` writes in `connect-database.sh` now append a key that is missing rather than only replacing one that exists. Against a hand-built `.env` lacking `DB_PASSWORD`, the run would print the generated password and silently fail to persist it.

### v1.20.1 (BETA) — 2026-10-03

- 🔒 `Security` - **The audit database and the TLS private key were readable by accounts that should not have them.** Measured on a real install: `data/` at `750` and `audit.sqlite` at `644`. `connect-database.sh` adds the `postgres` account to the `takextract` group so it can share the re-check folder, and that group could therefore traverse `data/` and read the audit log - which holds the TAK Server password in plaintext in `app_settings` (the backup route already redacts it, so the sensitivity was never in doubt), every account's password hash, and the hash-chained record itself. The Docker branch was worse: it only ever `chown`ed `./data` and never set a mode, leaving it world-readable. The self-signed TLS **private key** sat in the same directory with the same problem - `openssl req -keyout` writes it at the process umask - which let anyone on the host impersonate the server to every browser that had accepted its certificate. Fixed in four places so no single one has to hold: `setup.sh` sets `700`/`600` on both install branches, the systemd unit carries `UMask=0077`, and the app re-applies `0600` to both the database and the key on every start - which also corrects an install created before this.
- 🐛 `Bug Fix` - **The side-by-side service could never start.** `gunicorn.conf.py` calls `load_dotenv()` at import, and on that install shape `.env` is owner-only while gunicorn runs as the service account - so it raised `PermissionError` before the app was ever loaded, and systemd restarted it forever. One test box had crash-looped 159 times while reporting itself installed. systemd already supplies those values through `EnvironmentFile=`, read as root before privileges drop, so the call was redundant there; an unreadable `.env` is now treated as absent, while a malformed one still raises.
- 🐛 `Bug Fix` - **`setup.sh` reported a crash-looping service as running.** It accepted a single sighting of `systemctl is-active`, and under `Restart=` a service that dies immediately is briefly active after every restart. It is never `failed` either, because systemd keeps putting it back. It now waits past `RestartSec` and requires the service to be both still active and not to have restarted itself.
- 🐛 `Bug Fix` - **The one-time admin password could be missed entirely**, and it is generated once and never regenerated while an admin exists. The journal was dumped before gunicorn had imported the app. It now waits for output only the app produces, from this boot.
- 🐛 `Bug Fix` - **The `pg_control_system()` grant was never offered on a fresh install.** Its guard tested whether the database role already existed, captured before the role is created - so the step only ran on a re-run, and a new install silently reported "not granted" without asking. A new install is exactly when the cluster identifier should start being recorded.
- 🐛 `Bug Fix` - `check-database.sh` and the installer's baseline step failed on side-by-side installs for the same `.env` permission reason as the service, and are now handed their settings through a file only the service account can read - never through command-line arguments, which are world-readable via `/proc` and recorded in sudo's log.

### v1.20.0 (BETA) — 2026-10-03

- ✨ `New Feature` - **The minimum Python is now 3.10, so Ubuntu 22.04 installs with no third-party repository.** It was 3.12, matching the Docker image, which meant a side-by-side install on 22.04 - the common TAK Server host - needed Python from the `deadsnakes` PPA. On a restricted agency network that PPA can be unreachable outright: on the test host both `api.launchpad.net` and `ppa.launchpadcontent.net` resolved IPv6-only with no IPv6 route, opening the firewall for the first did not help because `apt` downloads from the second, and the install could not be completed at all. Ubuntu now needs only `apt-get install python3-venv` from the main archive. **This is a floor, not a target** - 3.12, 3.13 and later all satisfy it, nothing needs revisiting as newer releases ship, and the Dockerfile deliberately stays on `python:3.12-slim`.
- 🔧 `Improvement` - **`setup.sh` checks that the interpreter can actually build a virtual environment**, not just that its version is high enough. Debian and Ubuntu package `ensurepip` separately, so a stock 22.04 has `python3.10` but not `python3.10-venv` and `python3 -m venv` fails with *"ensurepip is not available"*. Without this the installer would find 3.10, declare success and then die at the venv step looking broken. It also probes newest-first (3.14 down to 3.10, then bare `python3`), so a host with a newer Python alongside the system one uses it automatically.
- 🔧 `Improvement` - **Both install paths now check their prerequisites before writing anything.** The side-by-side path checked for Python two-thirds of the way down: a real install created `.env`, chose a port, set a bootstrap username, generated a `SECRET_KEY` and asked the TLS question, and only then reported there was no usable Python - leaving a half-configured `.env` behind from a run that could never have finished.
- 🔧 `Improvement` - **CI runs five suites across Python 3.10 and 3.12.** It ran `test_auth.py` alone, on 3.12 alone. `requirements.txt` pins Flask but not Werkzeug, Jinja2 or itsdangerous, so the day one of those drops 3.10 support the two interpreters start resolving differently - the matrix is what catches that on a push rather than in somebody's install. `pip freeze` is logged for the same reason.
- 🐛 `Bug Fix` - The venv check's own failure branch aborted instead of printing its advice: the pipeline that captures Python's error fails by definition, and under `set -Eeuo pipefail` that propagated out of the command substitution - `set -e` is not suspended inside an `if` body. The operator saw *"failed at line N"* rather than which package to install. Found in the pre-push security review.

### v1.19.1 (BETA) — 2026-09-29

- 🐛 `Bug Fix` - **An update could pull successfully and rebuild nothing.** `connect-database.sh` leaves `.env` root-owned and `0600` because it holds the database password, so `docker compose` run as an ordinary account fails with `open .env: permission denied` - and it reports that and **stops**. `git pull && docker compose up -d --build` therefore pulled the new code and kept running the old, with nothing but one line of output to say so. It keeps the error now, prints it, and where it is a permission error says to use sudo, repeating the arguments that were given.

### v1.19.0 (BETA) — 2026-09-29

- ✨ `New Feature` - **A check for whether a TAK Server or PostgreSQL update changed the database underneath this tool.** `./check-database.sh` on the server runs every statement an export actually sends - from the same code that builds a package, so it cannot drift from it - and then checks the things that resolve perfectly well while returning the wrong answer: that `event_pt` is still a geometry in SRID 4326 (a different SRID makes the map-area filter return **nothing** rather than raise, so an export looks clean and is empty), that the channel bitmask still decodes to channel names, that callsigns still come out of the `detail` XML, and that the account still cannot write to any granted table. Read-only throughout: every statement is a `SELECT` in a `READ ONLY` transaction. Exit codes distinguish drift from breakage from not being able to connect at all, and a connection failure names what it usually is - a `pg_hba.conf` line a major-version upgrade did not carry across, a role that did not survive, a cluster on a different port, or `listen_addresses` back at `localhost` where a container on the Docker bridge cannot reach it.
- ✨ `New Feature` - **Every export records whether the database was still shaped as expected.** `connect-database.sh` now records the structure - tables, columns, types, PostGIS geometry columns - when it connects the tool, and every export compares against that record inside the snapshot it already holds, so it costs nothing and reads the same instant every file did. The result goes into the package README and the export's audit entry, which makes "the structure was as expected when this package was built" a fact recorded **with the package** rather than something that depended on someone running a check that week. A removed, retyped or reordered column is a failure because it changes what an evidence file contains; an added one is a warning naming where it landed and what it does to `<case>-cot_router-raw.csv`. **A difference is not reported as evidence that anything is wrong** - an upgrade changes structure legitimately, and the README says so in the same breath. An export never fails because of this. The System page gains a **Database structure** panel with the same summary and an Approve button that records who accepted a change.
- 🐛 `Bug Fix` - **A silent failure in the one file a re-check compares.** `cot_router_columns()` swallowed every exception and returned an empty list; `raw_rows_sql()` then quietly switched to `SELECT r.*`, whose values are typed by psycopg2 rather than cast to text by the server. `<case>-cot_router-raw.csv` is the one file a re-check compares by hash, so it could no longer match - and nothing anywhere said why. The failure is now recorded against the file the way `shapes.csv` already records missing deletions: the file still ships with its rows, and the README says what is wrong with it. The catalogue read also left the transaction aborted, so the next statement failed and was blamed for it; the snapshot is now restarted where the failure happened.
- 🔧 `Improvement` - The System page's **Test connection** ran `SELECT 1;` - it proved the credentials and the route and would have passed against an empty database, or one whose PostGIS was gone. It now also checks that PostGIS is installed, that `cot_router` exists, and that the account can actually read it, reporting each separately because they fail for different reasons and have different fixes. It still works for a candidate connection that has not been saved yet.
- 🔧 `Improvement` - Query text that lived inside `app.py` or inline inside `build_package` moved into `exports.py` with the rest of it - `POSITION_FILTER`, `single_csv_sql`, the record-count preview, the data-quality scan, the shape-deletions statement, the available-channels query. Both call sites alias what they used, so every existing reference is unchanged, and no SQL text changed, so a package built from the same window is byte-identical. The point is that the check executes the **real** statements rather than a copy of them that drifts. The one list that has to exist in two languages - the tables the installer grants - is now asserted equal between `exports.GRANTED_TABLES` and `connect-database.sh`.
